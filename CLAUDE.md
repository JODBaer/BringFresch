# Obsonare – Kontext für Claude

WG-Menüplaner (Schweizer Saisongemüse) mit Bring!-Anbindung. **Nur für die eigene WG**, kein Produkt.
Leitsatz: *einfach zu benutzen, einfach zu bekommen.* Neue Features erst nach dem Praxistest mit der WG.

WG: Joshua, Lukas, Leonie = Fleisch · Jo = Vegi (keine Veganer).

**«Obsonare 2.0.0 Umbau starten»** (Speicher-Umzug `bringfrisch_*` → `obsonare_*`, Schriftzug, Adressen): zuerst `docs/uebergabe-obsonare-2.md` lesen.

**Mehrere Chats gleichzeitig:** Vor der ersten Änderung an Code (`static/app.js`, `index.html`, `worker/`, `tests/`) einen eigenen Worktree anlegen (`EnterWorktree`), nie zu zweit im Hauptordner arbeiten. Nur eigene Pfade committen (`git add <pfade>`, nie `-A`), nicht stashen, keine fremden Dateien zurücksetzen, `tests/node_modules` nicht für andere umbauen. Fertig = `npm run ci` grün im Worktree → auf `main` → Worktree entfernen. **Ohne Warten (bevorzugt):** Zweig pushen, `gh pr create --fill` + `gh pr merge --auto --squash` → GitHub testet (`ci.yml`, Check «tests») und fügt bei grün selbst in `main` ein; mehrere PRs stellen sich an, keiner wartet auf den anderen. Rot = PR bleibt offen (Fotos als Artefakt). Direkter Push auf `main` geht weiterhin (Admin), aber ohne Prüfung.

## Architektur

- **`static/`** – PWA, Vanilla JS, keine Abhängigkeiten/CDNs, läuft offline. GitHub Pages (`https://jodbaer.github.io/BringFresch/`, Root-`index.html` leitet auf `static/` weiter).
  - `index.html` – nur Aufbau der Seite (Tabs, Dialoge); `app.css` – gesamtes Aussehen (vorher im `<style>` von `index.html`). CSS-Änderungen gehören nach `app.css`
  - `core.js` – reine Regeln ohne Bildschirm/Speicher/Netz (Woche, Portionen, Zutaten-Namen, Bring!-Katalog-Abbildung, Einkaufsliste, Wochenwahl-Regeln), abgelegt unter `BF_CORE`. Dieselbe Datei lädt die App per `<script>` und der Worker per `import "../../static/core.js"`; direkt in Node testbar (`tests/core.test.mjs`). Neue Regeln hierhin, nicht in die App-Dateien (`app*.js`)
  - `store.js` – Speicher auf dem Handy (`BF_STORE`): alle localStorage-Schlüssel an einer Stelle (gemeinsam / Abgleich / nur dieses Handy), `load`, `save`, `remove`. Neue Schlüssel hier eintragen; die App (`app*.js`) greift nie direkt auf `localStorage` zu
  - App = klassische Skripte (kein Bündler, kein Bau-Schritt) mit gemeinsamem Namensraum `BF_APP`, Reihenfolge wie in `index.html`: `app.js` – Grundlage (Konstanten inkl. `APP_VERSION`/`DEFAULT_SYNC_URL`, die die Build-Skripte hier ersetzen; Zustand `state` + Woche, Speichern, Hilfsfunktionen, `refresh()`), dann `app_plan.js` (Plan-Ansicht), `app_einkauf.js`, `app_vorrat.js` (Grundvorrat), `app_rezepte.js` (Rezepte & Saison, Katalog), `app_wahl.js` (Wochenwahl), `app_alle.js` («Alle Rezepte»), `app_sync.js` (Abgleich mit dem WG-Server, Bring! über den Bot), `app_einstellungen.js` (Einstellungen + Willkommen, Aktualisieren), `app_theme.js`, `app_start.js` (Navigation, Start). Was `app.js` anbietet, holt jede Datei oben mit `const { … } = app;`; aus anderen `app_*.js` heisst es `app.name` (erst nach dem Laden aller Dateien aufrufen). Aller Zustand liegt in EINEM Objekt `state` (auch `state.viewNext`, `curPlan`, `nextDoc`, `vote`, `sync`, `mySites`, Push-Timer); `app.subscribe(fn)` meldet Abonnenten an, `refresh()` ruft sie danach (`app.notify()`). Migrationen (Altlasten, alte Wochenwahl) stehen an einer Stelle: `BF_STORE.migrate(woche)`. Neue Datei → `index.html` + `STATIC_ASSETS` in `sw.js` (`tests/assets.test.mjs` prüft das); jsdom-Tests laden die Seite über `tests/app_html.js`
  - `standalone_data.js` – Grundvorrat, VSGP-Saisondaten (`season_items`), Monatsnews, 10 Klassiker-Rezepte
  - `recipes_imported.js` – generiert von `tools/import_recipes.py merge`, nicht von Hand ändern
  - `recipe_importer.js` – eigene Rezepte (localStorage)
  - `sw.js` – Network-First, nach 2.5 s ohne Antwort aus dem Cache (schwacher Empfang); bei Asset-Änderungen `CACHE_NAME` hochzählen (im Release setzt `build_site.mjs` die Version ein)
- **`worker/`** – Cloudflare Worker (Free): Bring!-Sync über ein Bot-Konto (Secrets), Wochenwahl + Plan in KV, iCal-Abo `/cal/:token.ics`, Rezept-Link-Import. PIN-geschützt (`X-WG-PIN`). Setup: `worker/README.md`. Dateien in `worker/src/`: `index.js` (Endpunkte), `auth.js` (WG, PIN, Sperre), `speicher.js` (Speichern mit Abgleich, Sicherung), `bring.js`, `kalender.js`, `rezept.js` (Link-Import, Bilder), `http.js` (Antworten, CORS, sicheres Abrufen).
- **`tools/import_recipes.py`** – höflicher Import (schema.org; robots.txt, 3 s Abstand pro Seite) von Betty Bossi, Migusto, Fooby, Swissmilk und den Branchen-Seiten. Nur Fakten, keine Texte. Kein Massen-Scraping: nur gezielt (`add`, `nutrition`) und der Monatsabgleich (`monthly`); Regeln ohne Netz in `tools/test_import_recipes.py`. Bilder: nur das Vorschaubild (og:image) holt der Worker einzeln beim ersten Anzeigen in der Wochenwahl (`/img`, KV `img:<sha1>`, nur mit PIN, nicht in der Sicherung) – nie ins öffentliche Repo.

Ohne Worker: alles lokal, Bring! via Teilen/Kopieren.

**Mehrere WGs** (ein Worker): Header `X-WG` (Name) + `X-WG-PIN`. Erste WG = `MAIN_WG` (`wrangler.toml`, «allmen,wg1»: erster Name gilt, weitere = Aliasse, Secret `WG_PIN`, Daten ohne Präfix); weitere WGs `wgs:<name>` in KV (PIN-Hash, `node tools/new_wg.mjs "Name"`), Daten unter `w:<name>:…`. Gleicher Bring!-Bot; jede weitere WG muss ihre Liste selbst wählen, Listen anderer WGs sind nicht wählbar (`listowner:<uuid>`). 10 falsche PINs = 15 Min. Sperre pro WG und Absender (IP), auch für die erste WG; unbekannte WG-Namen schreiben nichts in KV.
**Geteilte Rezepte**: alle WGs greifen auf denselben Rezept-Bestand zu. Eigene Rezepte sind standardmässig geteilt (`shared !== false`, im Formular «Mit allen WGs teilen»); der Worker legt sie beim Speichern von `/settings` unter `shared:<wg>` ab (gemeinsamer Speicher, Liste `shared:index`, `worker/src/geteilt.js`), `GET /recipes/shared` liefert die der anderen WGs (Ids `x-<wg>-<id>`, `shared_from: true`; Herkunft wird nicht gezeigt, nur «geteilt»). Die App speichert sie zwischen (`bringfrisch_shared_recipes`) und nimmt sie in `allRecipes()` auf (Katalog-Filter «Andere WGs», Wochenwahl). Stimmen/Rangliste bleiben pro WG. Fremde Rezepte nur «Anpassen» (eigene Kopie).
**Erster Start** (nicht verbunden): Willkommen mit WG-Name + PIN (= Zustimmung zu `static/rechtliches.html`, gespeichert in `bringfrisch_terms`), dann «Wer bist du?» (leere WG: sich selbst eintragen). «Ohne WG ausprobieren» = lokal.

## Fachregeln

- **Einkauf/Vorrat-Reiter** (Entwurf `docs/design/einkauf-sublime.html`, Joshua 13.11.): Liste ohne Kasten, Reiter mit Trennstrichen, Umschalter **Rezept / Kategorie** (pro Handy `bringfrisch_shop_sort`, gilt für Kaufen und Vorrat), Wischen wechselt die Reiter. Vorrat: gleiche Abschnitte wie Kaufen, «Woche gekocht» oben in der Kopfzeile, **Name antippen = für Bring! vormerken** (wie in Kaufen, Vermerk «→ Bring!»), **sonst Zeile antippen oder Name lange drücken = Blatt** (dort Leer · Fast leer · Halb · Voll) (Joshua 14.11.). Ein Bring!-Knopf unten rechts (`#shopFab`): öffnet die Gegenüberstellung, nach dem Senden 10 s «Rückgängig» im Knopf; auf der Einkauf-Seite kein 🛒 oben, keine Leiste «Für Bring!», kein Bring!-Chip im Kopf. Reiter «Auf Bring!» bleibt wie bisher (Joshua 14.11.). In «Kaufen» Zeile antippen = **vormerken** (durchgestrichen, bleibt stehen), gesendet erst mit dem Knopf; die Gegenüberstellung wählt dann nur die Vorgemerkten aus dem Plan vor.
- **Alle Rezepte** (Joshua 14.11.): Knopf «Alle Rezepte ansehen» in der Zeile «Meine Rezepte» (Reiter Rezepte) → ganze Seite zum Durchscrollen, kleine Memory-Karten (3 pro Zeile), nach Herkunft (Eigene, Swissmilk, Fooby, Betty Bossi, Migusto, andere Seiten, Klassiker, andere WGs; `CORE.groupBySource`), darin zuerst was jetzt Saison hat, «Gerade nicht Saison» am Schluss der Herkunft. Karte antippen = umdrehen, Tag Mo–So antippen = einplanen (angezeigte Woche, ab Do umschaltbar), mit «Rückgängig».
- **Einkauf nach Gericht** (nicht nach Abteilung): `groupByDish` in `core.js`, Gemeinsames unter «Für mehrere Gerichte». **Beliebtheit** = Stimmen der Wochenwahl dieser WG (Worker zählt nach jeder Stimme in `pop`, `GET /popular`), sortiert den Katalog. **Tauschen**: Menü-Blatt «Tauschen mit», `swapDishes` (Esser/Gäste/Puffer/Zeit bleiben am Tag).

- **Nächste Woche** (ab Donnerstag): Chip «KW 47 →» in der Abschnittszeile bzw. Wischen; eigener Plan pro KW (`bringfrisch_next_plan`, Worker `/plan/:week`), `state.plan` ist immer die angezeigte Woche. Offene Tage (`empty: true`) kaufen nichts und stehen nicht im Kalender. Wochenwahl pro Woche gespeichert. Montag: geplante Woche wird zur laufenden.
- **Ablauf**: Wochenwahl (14 Saison-Gerichte, ½ vegi / ½ Fleisch, Top 7 → Tage mit anwesenden Fans, Wunschtag zählt) → Plan (Esser pro Tag, Puffer) → Bring! füllen. **Tag pro Gericht** (Joshua 19.11., Entwurf `docs/design/wahl-tage-entwurf.html`): im WG-Ranking steht bei den Top 7 der vorgeschlagene Tag (★ Wunschtag, 🏠 Fans daheim), antippen = Mo–So, belegter Tag tauscht (`CORE.rankDays`/`moveDay`); nur auf dem Handy, das übernimmt. Haben alle gewählt, springt die Wochenwahl beim Öffnen zum Ranking. Platz 8+ mit Stimme kommt in die Wochenwahl der nächsten Woche (höchstens 4, «von letzter Woche», `CORE.carryOver`, aus der Vorwoche auf diesem Handy). Meldung antippen schliesst Offenes und öffnet bevorzugt die installierte App; installiert = nur kleines Symbol (`icon-badge-96.png`), im Browser mit grossem Bild. Standort der Hofläden ist unter Einstellungen ausschaltbar.
- **Portionen** = Esser + Gäste + Reste-Puffer (Standard +2, wählbar +0…+6). Niemand zuhause → kein Kochen.
- **Rezeptmengen** gelten für `recipe.servings` (Standard 4).
- **Stück-Zutaten** (Joshua 18.11., endgültig): im Plan zum Kochen auf **halbe** Stück genau (1 Zwiebel für 4, gekocht für 2 = ½ Zwiebel; `CORE.formatCookAmount`), eingekauft wird **ganz** (Einkaufsliste rundet die Wochensumme auf, `formatAmount`). Salz/Pfeffer/«einige …» nicht umrechnen.
- **Nährwerte** (Joshua 19./20.11.): pro Mitbewohner eine Auswahl Ernährung + Ziel – «Fleisch», «Fleisch · proteinreich», «Fleisch · leicht», «Vegi …», «Vegan …» (`CORE.DIET_CHOICES`; auch beim Hinzufügen und im Willkommen), gespeichert getrennt als `member.diet` + `member.goal` (`protein` | `kcal`, in `/settings`). Randnotiz «≈ 640 kcal · 32 g Protein» im offenen Plan-Tag, im Katalog (Filter «Proteinreich»/«Leicht») und als Vermerk auf der Wahl-Karte – gerechnet für «Ich bin» wie der Einkauf (Rezeptportion, Vegis ohne das Fleisch daraus, + Extra-Fleisch/Grillkäse/Vegi-Ersatz + Salat). Quelle: `recipe.nutrition` (Rezeptseite, schema.org, pro Portion: `import_recipes.py nutrition`, Worker `/recipe`, geteilte Rezepte) vor der Schätzung aus den Zutaten (`CORE.nutritionFor`, Tabelle `NUTRIENTS` in `core.js`). Geschätztes wird nie gespeichert; bei zu vielen unbekannten Zutaten keine Zahl.
- **Alles für alle**: gemeinsame Basis + 150 g Fleisch pro Fleisch-Esser (nicht bei Fleischrezepten) + 100 g Grillkäse pro Vegi + 50 g Salat pro Portion.
- **Grundvorrat** (Variante C, erste Fassung 12.11.2026, Entwurf `docs/design/grundvorrat-varianten.html`): Mengen pro Artikel (`qty`, `unit` Znacht/Stk, `pack`, `size`, `since`, `weekly`, `empties`, `booked`, `checked` im Vorrat-Dokument; altes Format mit nur `in_stock` gilt weiter: `in_stock === false` = leer, Menge fehlt = volle Packung; neue Handys halten `in_stock = qty > 0`). Regeln in `core.js` (`isKnapp`: 2 oder weniger, bei 1–2 Stück pro Packung erst unter einer Packung; `bookWeek`/`unbookWeek`; `boughtStaple`). Beim Einkauf: «Kaufen» + «Aus dem Vorrat – wird knapp», Bereich «Vorrat» als Liste (antippen = leer, Schalter «Woche gekocht» bucht ab, «Alles da» aufklappbar), Leiste «Für Bring!» → «Prüfen» = Gegenüberstellung Kaufen | Vorrat. **Nichts aus dem Vorrat geht ungefragt auf Bring!** (erst mit dem Knopf, Vermerk «Vorrat · Packung»). In Bring! gekauft/abgehakt (vom Bot gesetzt) = eine Packung dazu. «Grundvorrat verwalten» = Kacheln (3 pro Zeile, Abteilung/Dringend), Blatt pro Artikel, lange drücken = − + und ✕, Inventur am Ende.
- **Wahrheit**: Bring! = was auf der Liste steht (Obsonare baut nur drumherum). Grundvorrat = Obsonare, gemeinsam für die WG im Worker (`/vorrat`).
- **Abgleich** (Plan, nächste Woche, Vorrat, Einstellungen): kein Uhrenvergleich. Das Handy merkt sich pro Dokument den Stand des Servers beim letzten Abgleich (`bringfrisch_base_*`: Stempel + Inhalt) und schickt den Stempel als `base` mit; hat inzwischen jemand gespeichert (Stempel des Servers **neuer** als `base`), antwortet der Worker 409 und die App führt zusammen (pro Tag / Artikel / Einstellung gewinnt, wer seit dem gemeinsamen Stand geändert hat). Ein **älterer** Stempel vom Server ist nie ein fremder Stand, sondern verspätetes Lesen (KV liefert kurz nach dem Speichern noch alt) und wird nicht übernommen. Test: `tests/sync_merge.test.mjs` (auch mit verzögertem Speicher).
- **WG-Einstellungen** gemeinsam im Worker (`/settings`): Mitbewohner, Znacht-Zeit, Rezept-Webseiten, eigene Rezepte. «Speichern & an alle senden» schickt sofort. Pro Handy bleiben: PIN, «Ich bin», Stil, Farben. Ab 5 Personen im Plan zwei Reihen (5 = 3 + 2).
- **Bot löscht nur Eigenes**: der Worker merkt sich in KV (`bot:<liste>`), was er neu gesetzt hat; nur das nimmt er weg, und nur wenn es noch drauf ist. Bring! liest kurz nach dem Schreiben manchmal noch alt: was der Bot gesetzt, aber noch nie auf der Liste gesehen hat (`seen: false`), bleibt 5 Min. seins und lässt sich per Name wegnehmen; schon Gesehenes, das fehlt, gilt als gekauft.
- **Herunterziehen** (oben auf der Seite) = sofort synchronisieren: eigene Änderungen (Plan, Vorrat) hoch, dann Stand der anderen holen.
- **Benachrichtigungen** (Joshua 19.11., Plan `docs/plan/benachrichtigungen.md`, Entwurf `docs/design/benachrichtigungen-entwurf.html`): Web Push vom eigenen Worker (`worker/src/push.js`, VAPID-Secrets `VAPID_PUBLIC`/`VAPID_PRIVATE` aus `tools/vapid.mjs`, ohne = 501), App `static/app_push.js` (Karte unter Einstellungen, pro Handy `bringfrisch_push`). Erste Stimme einer Person pro Woche → Meldung an alle anderen («Leonie hat für KW 48 gewählt · Noch offen: …»), letzte Stimme → alle «Alle haben gewählt». **Anstupsen** in der Wochenwahl: wer fehlt und Meldungen hat, höchstens 1× pro Tag. **Ruhezeit 21–8**: Wahl-Meldungen und Anstupser warten (`pushq`, Cron). **Markt/Hof 1× pro Woche**: Ort aus der Hofläden-Liste (Suche Name des Bauern oder Ortschaft, `CORE.searchFarms`) oder selbst eingetragen, Tag (bei bekannten Zeiten nur offene Tage), Zeitpunkt wählbar: Vorabend 19:00 / 30 Min. vor Öffnung / fest (`CORE.marketDue`); nur wenn auf Bring! etwas steht, Winterpause = nichts. **Nach Ort** geht nur per iPhone-Kurzbefehl («Ankommen bei …» → `GET /erinnerung/:token`, ohne PIN, Text höchstens 1× pro Woche). iPhone-Push nur mit Obsonare auf dem Home-Bildschirm. Cron alle 15 Min. (Sicherung nur um 03:00 UTC).
- **Schon drauf?** Fehlendes wird einfach eingefügt. Steht etwas schon auf Bring!, fragt «Bring! füllen» pro Artikel nach: Bot-Artikel mit neuer Menge (z.B. zweites Rezept mit Rahm) vorausgewählt, fremde Einträge nicht (Menge wird ergänzt). Danach «Rückgängig»: neue Artikel weg, alte Mengen zurück.
- **Schnelles & Reste** (`quick: true` in `standalone_data.js`): Fertigpizza, Nuggets, Maultaschen, Gnocchi, Dumplings, Abendbrot, Café complet, Birchermüesli, Spaghetti mit Pesto, Fischstäbli, Toast Hawaii, Ravioli, Resteessen. 2 davon pro Woche im Memory. `vegi_swap` ersetzt den Grillkäse (z.B. Vegi-Nuggets), `no_addons` lässt Extra-Fleisch/-Käse weg, `no_salad` den Salat (Müesli, Fondue …), `is_leftovers` = nichts einkaufen.
- **Rezepte = ein Katalog für alle WGs** (`standalone_data.js` + `recipes_imported.js`, dazu die eigenen Rezepte der WG). Pro WG gespeichert werden nur IDs (Wochenwahl, Plan). Die Wochenwahl hat nie dasselbe Gericht zweimal (gleiche ID, gleicher Titel oder gleicher Link, `CORE.sameDish`); doppelte Listen vom WG-Server werden beim Öffnen bereinigt, auf 14 aufgefüllt und zurückgeschrieben (`CORE.cleanCandidates`). **Monatsabgleich** (Joshua 23.11.): am 25. jedes Monats gleicht `.github/workflows/rezepte-monat.yml` (`import_recipes.py monthly`) alle importierten Rezepte mit ihren Webseiten ab (Zutaten, Portionen, Zeit, Nährwerte; Seite weg = Rezept weg; Titel/id bleiben, Ernährung nur strenger) und fügt 3 neue Znacht ein, die im nächsten Monat Saison haben (je ein vegi und ein Fleisch zuerst, mit Nährwerten bevorzugt); nur bei grünen Tests direkt auf `main`, Bericht im Lauf.
- **Bring!-Bilder**: Namen werden auf den Bring!-Katalog (`static/bring_catalog.js`, erzeugt von `tools/update_bring_catalog.mjs`) abgebildet, z.B. Butternuss-Kürbis → Kürbis; die genaue Sorte steht in der Mengenangabe. Unbekanntes (v.a. Gewürze) bleibt eigener Artikel. Eigene Bilder hochladen kann die Bring!-API nicht.
- **Einkaufsnamen**: «Schweizer», Klammern, «à ca. 400 g» stehen in der Mengenangabe, nicht im Namen. Leitungswasser kommt nie auf die Liste.
- **Design**: Plan-Ansicht + Navigation nach `docs/design/Obsonare-Plan-Redesign.md` (massgeblich) und dem Prototyp `docs/design/obsonare-prototyp.html` (`?os=ios` / `?os=android`). iPhone = Glas-Stil (`html.glass`), Android = Material 3 Expressive (`html.m3`), automatisch erkannt, umschaltbar unter Einstellungen → «Mehr» (kein ⋮-Menü mehr; Einstellungen ist direkt eine Seite). Farben Hellgrün #90EE90 + Pistazie #93C572 (Standard; Akzent und Hintergrund pro Handy wählbar: je 3 Vorgaben + eigene Farbe, Tokens werden in `applyTheme` berechnet – im CSS keine festen Grüntöne, nur Tokens), Schrift Roboto Flex (lokal in `static/fonts/`, kein CDN), Hell/Dunkel folgt dem System, pro Handy umschaltbar unter Einstellungen → Stil (Automatisch / Hell / Dunkel, `bf-mode`; CSS nur über `html.dark`, nie `prefers-color-scheme`). Mit einem offenen Tag müssen alle 7 Tage sichtbar bleiben (Dichte d1–d3 einmal beim Start/Drehen, Zutaten notfalls mit Höchsthöhe); beim Aufklappen bewegt sich nur der offene Tag. Prüfen: `node tests/layout_check.mjs --shots` (Edge/Chrome). Einkauf, Rezepte & Saison, Einstellungen sind noch im alten Stil. Joshua entscheidet Design-Fragen gern selbst – live als HTML zeigen.

## Befehle

```bash
cd tests && npm ci && npm run ci        # ALLES vor dem Abschluss: Syntax, App, Integration, Worker, Layout → «PASS: alles grün»
npm run ci -- --pr                       # PR-Prüfung (ca. 2 Min): schnelle Tests + Browser nur nach geänderten Dateien (docs/teststrategie.md)
npm run ci -- --no-layout                # ohne Browser (falls gesperrt); --shots = Fotos in tests/shots/
npm test                                 # nur App (jsdom), Zutaten-Abgleich, 2-Handy-Integration, Worker
node zutaten.test.js --update            # nach bewusster Änderung am Grundvorrat-Abgleich: tests/snapshots/vorrat_treffer.json neu schreiben
node tests/layout_check.mjs --shots      # Plan-Layout im echten Browser (390×844, 375×667, 390×600)
cd tests && node links_live.mjs          # Rezept-Links im Browser öffnen (Internet, nur von Hand); falsche Links ersetzen oder entfernen → App zeigt «Rezept suchen» (Fooby)
cd tests && npm run ui                  # UI-Test: klickt sich wie ein Mensch durch alle Seiten/Funktionen (echter Chrome, Worker-Code + Bring!-Attrappe im Prozess)
cd tests && npm run ci                  # alles (auch Layout + UI); --no-ui / --no-layout; ohne Browser: npm run chrome
npx serve static                        # lokal ansehen
node tools/build_architektur.mjs         # Architektur-Übersicht (docs/design/obsonare-architektur.html): eingebautes Handy aus static/ neu bauen; Namen prüft tests/architektur.test.mjs
git tag v0.3.0 && git push origin v0.3.0 # Release: Tests in CI, nur bei grün GitHub Pages (WG-Version)
node tools/build_stage.mjs               # Test-Version bauen (dist-stage/, Test-Server, «TEST»-Band)
cd worker && npx wrangler deploy        # Worker von Hand (normal: per Release-Tag)
```

Test-Version: `stage.yml` bei jedem Push auf main → **sofort** (getestet wurde schon im PR; keine doppelten Offline-Tests mehr) **ein** Worker `bringfrisch-test` = Test-Seite (Assets aus `dist-stage/`) + Test-Server (`wrangler deploy --env stage`, `ONLY_LIST_NAME=Home-test`, `MAIN_WG=test`) → Live-Test `tests/stage_live.mjs` gegen Bring! «Home-test» (Secret `STAGE_PIN`). Der Test-Server darf nie in die WG-Liste schreiben. Auf dem WG-Server ist «Home-test» eine Spielwiese: wählbar nur für WGs ohne eigene Liste, gehört nie einer WG (kein `listowner`).
**Test-Freigabe** (Joshua 19.11.): In der Test-Version ist das orange «TEST»-Band ein Knopf («3 neu ›») → Blatt «Neu zum Testen» mit den Änderungen seit dem letzten Release-Tag (`freigabe.json`, von `build_stage.mjs` erzeugt) → **Freigeben** (Test-Server setzt den nächsten Tag `v…+0.1.0` auf main → deploy-pages.yml) oder **Problem melden** (GitHub-Issue). Nur in `dist-stage/` (`tools/stage/freigabe.js`), die WG-App enthält nichts davon. Test-Server: `worker/src/freigabe.js`, Secret `RELEASE_TOKEN` (fein-granular, nur dieses Repo: Contents + Issues schreiben, Actions lesen; läuft nach 1 Jahr ab), nur mit der Test-PIN; freigegeben wird nur, was gerade auf main liegt.
**Teststrategie** (`docs/teststrategie.md`, Pareto/Lean): PR = `ci.yml` mit `npm run ci -- --pr` (schnelle Tests + UI-Kernabläufe/Layout nur bei passenden Änderungen); Release = alles. **Auto-Release** (`release-auto.yml`, `tools/release_decide.mjs`): seit dem letzten Tag nur `fix`/`docs`/`test`/`chore`/`ci` → nach der ganzen Release-Prüfung automatisch Tag `v…+0.0.1`; ein `feat` dabei → wartet auf die Freigabe in der Test-App. PR-Titel daher immer mit Typ (`fix(…): …`, `feat(…): …`).
CI: `.github/workflows/deploy-pages.yml` läuft bei Tags `v*`, von Hand oder aus `release-auto.yml`: Job `test` (`npm run ci -- --shots`, Fotos als Artefakt bei Fehler), danach `worker` (WG-Server per Wrangler, braucht Secrets `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID`, sonst Warnung) und dann `deploy` (Pages: `index.html` + `static/`, damit `/static/` gleich bleibt). Push auf main veröffentlicht nur kleine Fixes (release-auto.yml), neue Funktionen erst nach der Freigabe. Worker sichert täglich alle KV-Daten (`backup:<Tag>`, 30 Tage, `worker/README.md`).
**Issue-Agent** (`.github/workflows/issue-agent.yml`, 1. und 15. des Monats oder von Hand): Claude liest die offenen Issues, kommentiert pro Issue Ursache, Vorschlag, Aufwand und einen fertigen Prompt für einen Agenten (Label `agent-analysiert`) und pflegt das Plan-Issue «📋 Issue-Plan» (Label `issue-plan`). Ändert nie Code. Braucht Secret `CLAUDE_CODE_OAUTH_TOKEN` (`claude setup-token`) oder `ANTHROPIC_API_KEY`, sonst nur Warnung.
Tests sind deterministisch: `tests/determinism.js` (feste Uhr Di 10.11.2026, fester Zufall), kein Netz (fetch, Bring!, KV nachgebaut). Neue Tests genauso; neue Funktion in der App = neuer Schritt in `tests/ui_e2e.mjs` (Anleitung: README «Neuen Test hinzufügen»). Live-Tests (`tests/e2e_live.*`, `tools/check_live.*`) brauchen Zugangsdaten → nur von Hand, nie in CI.
