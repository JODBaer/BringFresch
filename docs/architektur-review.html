Warum app.js kaum kleiner ist: Herausgelöst wurden die Regeln; die Ansichten sind noch drin. app.js ist eine einzige Funktion, in der sich rund 150 Funktionen über gemeinsame Variablen aufrufen. Das Aufteilen («Variante 4») heisst echte Browser-Module und die jsdom-Tests umbauen, weil diese die App heute durch Einsetzen des Dateiinhalts laden. Das braucht ein ruhiges Zeitfenster, in dem kein anderer Chat an app.js arbeitet.

Was als Nächstes offen ist

  1. Variante 4: zuerst die Test-Lader auf Module umstellen, dann Ansicht für Ansicht herauslösen, mit einem Zustand statt losen Variablen (Schritte 3 und 5).
  2. Bring! in einem Aufruf: hebt das 45-Artikel-Limit auf; braucht zuerst einen Live-Test gegen «Home-test».
  3. Schrift kürzen: Roboto Flex 196 KB, mit optischem Vergleich.
  4. Grundvorrat Variante C: Richtung entschieden, Einzelheiten mit Joshua offen. Gebaut wird nach dem Umbau, damit die Ansicht nur einmal angefasst wird.

Refactoring-Plan

Jeder Schritt ist einzeln releasbar und endet mit grünem npm run ci. Die ausführliche Fassung für die Arbeit liegt im Repo unter docs/refactoring-plan.md.

  1. 0 ✓

    Fehler flicken, ohne Umbau (erledigt)

    Abgleich auf ganze Wörter statt Teilwörter, mit Test über alle Zutaten. PIN-Sperre auch für die erste WG.
  2. 1 ✓

    Sicherheitsnetz (erledigt)

    Ein Schnappschuss-Test: Einkaufsliste und Bring!-Einträge für jedes der 98 Rezepte. Danach fällt jede ungewollte Änderung beim Verschieben auf.
  3. 2 ✓

    Regeln herauslösen (erledigt, Variante 3)

    static/core.js: Woche, Portionen, Zutaten, Einkaufsliste, Wochenwahl als reine Funktionen. App und Worker laden dieselbe Datei, Tests laufen direkt in Node. Kein Bündler.
  4. 3 ½

    Ein Zustand, ein Speicher (Speicher erledigt, Zustand offen)

    static/store.js bündelt alle localStorage-Schlüssel. Offen: state plus die losen Variablen (viewNext, curPlan, nextDoc, sync) in einem Objekt – gehört zu Variante 4.
  5. 4 ✓

    Sync mit Versionsnummern (erledigt)

    Der Server-Stempel dient als Version. Die App schickt mit, worauf sie aufbaut. Bei Konflikt wird pro Tag bzw. pro Artikel zusammengeführt statt überschrieben. In v1.7.3 korrigiert: ein verspätet gelesener alter Stand überschreibt eigene Änderungen nicht mehr.
  6. 5 ½

    Ansichten und CSS aufteilen (CSS erledigt, Ansichten offen)

    CSS liegt in static/app.css. Die Ansichten aus app.js herauslösen ist Variante 4 (Module + Tests umbauen).
  7. 6 ½

    Worker aufteilen, Bring! schneller (aufgeteilt, Anmeldung gemerkt; Batch offen)

    index.js plus auth, speicher, bring, kalender, rezept, http. Offen: Artikel in einem Aufruf senden (hebt das 45er-Limit auf).
  8. 7 ✓

    Schneller Start bei schwachem Empfang (erledigt)

    Der Service Worker wartet höchstens 2.5 s aufs Netz und liefert dann aus dem Cache: 2.6 s statt über 15 s bei sehr langsamem Netz. Cache-Name kommt im Release aus der Versionsnummer.
  9. 8

    D1 nur bei Bedarf

    Der Entwurf in docs/plan-d1.md ist gut, lohnt sich aber erst für geteilte Rezepte zwischen WGs. Für eine WG reicht KV nach Schritt 4.

Entschieden (11.11.2026): zuerst Variante 3 (eine Regel-Datei als gewöhnliches Script, ohne Bündler), später Variante 4 (echte Browser-Module). Kein esbuild. Der Worker importiert core.js trotzdem direkt.

Hosting

Cloudflare Workers Free passt: kein Kaltstart, keine Kreditkarte, und eine WG braucht einen Bruchteil der Freigrenzen. Die engste Grenze sind die KV-Schreib- und Listen-Aufrufe (1000 pro Tag fürs ganze Konto). Vier Personen liegen darunter, aber der Live-Test der Test-Version zählt mit; das steht bereits als offener Punkt in plan.md.

VarianteKostenHaken
Cloudflare Workers + KV (heute)0KV ist nicht sofort überall gleich (bis ca. 1 Min. Verzögerung). Für eine WG selten spürbar.
Cloudflare D1 dazu0Mehr Code. Nur für geteilte Rezepte nötig.
Supabase / Firebase0Supabase pausiert unbenutzte Gratis-Projekte; beide bringen Konten und SDKs mit, die Entscheid 11 (keine fremden Abhängigkeiten) widersprechen.
Render / Fly0 bis ca. 5 USD/MonatGratis-Stufe schläft ein. Deswegen wurde gewechselt (Entscheid 6).
Eigener kleiner Serverca. 4 CHF/MonatUpdates, Sicherung, Zertifikate selbst pflegen.

Eine mögliche Vereinfachung: Die Test-Version liefert Seite und Server schon aus einem Worker aus. Das ginge auch für die WG-Version: eine Adresse, ein Deploy, kein CORS. Der Preis ist eine neue Adresse, also müssten alle die App einmal neu auf den Homescreen legen und sich neu verbinden. Ich würde es erst machen, wenn ohnehin ein Grund für eine neue Adresse kommt.

Die Freigrenzen stammen aus meinem Wissensstand, nicht aus einer heutigen Abfrage. Vor einem Umbau, der sich darauf verlässt, kurz bei Cloudflare nachsehen.
